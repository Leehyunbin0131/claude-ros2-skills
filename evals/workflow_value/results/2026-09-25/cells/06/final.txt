`PowerReading` now carries `power_w` and `valid`, and both monitors output watts for valid readings and NaN for invalid ones. The CI-style build and tests pass, and a live test of the installed nodes gave the right output. Nothing is committed.

## What changed

- **`power_interfaces/msg/PowerReading.msg`**: replaced `float64 power_mw` with `float64 power_w` (watts) and added `bool valid`, with comments.
- **`power_interfaces/CHANGELOG.rst`**: added a "Forthcoming" entry at the top noting the breaking field change and the new `valid`. Version numbers are unchanged, as CONTRIBUTING asks.
- **`power_py_monitor/conversion.py`**: `normalize(msg)` returns `msg.power_w` when `msg.valid` is true, otherwise `math.nan`. The division by 1000 is gone.
- **`power_cpp_monitor/src/conversion.cpp`** (plus the doc comment in `conversion.hpp`): same logic, using `std::numeric_limits<double>::quiet_NaN()`. The function signature is unchanged.
- **Tests**: the old milliwatt tests are replaced. Each package now has one test for a valid reading (12.5 in, 12.5 out) and one for an invalid reading (NaN out).
- **The `monitor` nodes needed no code change.** They already publish whatever `normalize()` returns. Helper names, executables and topic names are unchanged, as the README requires.

## How I verified it

1. **CI-style run:** I copied the sources to a clean directory (`/tmp/power-ci.SbKn6J`) and used a shell with only `/opt/ros/jazzy` sourced. `colcon build` and `colcon test --return-code-on-test-failure --python-testing pytest` both exited 0. A results checker confirmed all 4 new tests actually ran and passed, rather than the test step passing with zero tests.
2. **Rebuilt your workspace's `install/`**, again with only Jazzy sourced so the old build couldn't mask problems.
3. **Live test:** in a fresh shell with the new `install/setup.bash` sourced, on an isolated ROS domain (ID 87, localhost only):
   - `ros2 pkg prefix` resolved both packages to this workspace's `install/`.
   - `ros2 interface show` showed the new message definition.
   - With both installed `monitor` executables running, I published two readings to `/sensor/power`:
     - `power_w=12.5, valid=True` → `/monitor/py_power_w` = 12.5, `/monitor/cpp_power_w` = 12.5
     - `power_w=7.25, valid=False` → both `nan`

   I then stopped only the two processes I had started.

## Things to be aware of

- **This breaks anything that publishes `/sensor/power`.** The sensor driver isn't in this workspace, so I couldn't update or test it. It must now send watts and set `valid`.
- **`valid` defaults to `false`.** A publisher that fills `power_w` but never sets `valid` will make both monitors output NaN.
- **Restart running nodes.** Your terminal's paths still point to the rebuilt `install/`, so new processes get the new message. Any nodes that were already running still use the old definition and need restarting.
- **An existing gap, not changed:** `power_cpp_monitor` installs the `conversion.hpp` header, but the `power_cpp_monitor_conversion` library itself is never installed. C++ tools outside this package that call `normalize` can't link against it.
