`RangeReading` now carries `distance_m` (metres) and `valid`, and both `normalize` helpers return the distance when `valid` is true and NaN when it is false. A clean build and all tests pass the way CONTRIBUTING describes, and both monitor nodes gave the right output when I ran them.

## What I changed
- **`src/range_interfaces/msg/RangeReading.msg`**: `float64 distance_cm` is replaced by `float64 distance_m` and `bool valid`, with comments for both.
- **`src/range_interfaces/CHANGELOG.rst`**: added a "Forthcoming" entry at the top noting that this breaks every consumer. I didn't bump any versions, as CONTRIBUTING asks.
- **Python, `range_py_monitor/conversion.py`**: `normalize(msg)` returns `msg.distance_m` if `msg.valid`, otherwise `math.nan`. I removed the `SCALE = 100.0` constant because nothing needs it now.
- **C++, `src/conversion.cpp`**: same logic, returning `std::numeric_limits<double>::quiet_NaN()` when the reading is invalid. I also updated the doc comment in `conversion.hpp`. The function signature is unchanged.
- **Monitor nodes**: no code changes. Both already publish `normalize(msg)`, so they get the new behaviour automatically. The helper names, executables and topics in the README are unchanged.
- **Tests**: in both packages, the old centimetre test is replaced by one test with a valid reading (expects `2.5`) and one with an invalid reading (expects NaN).

## Things you should know
- **Your terminal is out of date.** I didn't touch the workspace's `build/`, `install/` or `log/`, so they still contain the old `distance_cm` message. To pick up the change, run `colcon build`, then `source install/setup.bash` again in your terminal. The old and new messages are incompatible, so anything still publishing `distance_cm` has to be rebuilt too.
- **Default is invalid.** An empty `RangeReading()` now has `valid = false`, so it produces NaN. That seemed the safer default, but it means publishers must set `valid: true` explicitly.
- **Existing issues I left alone:**
  - `colcon build` prints a setuptools warning about `tests_require` in `setup.py`. It doesn't affect the build.
  - The README says other tools call the C++ `normalize` directly, but `CMakeLists.txt` installs only the header, not the `range_cpp_monitor_conversion` library, so code outside this package can't link against it. That seemed out of scope here, but it's worth fixing separately.
