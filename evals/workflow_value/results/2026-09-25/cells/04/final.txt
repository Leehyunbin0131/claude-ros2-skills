The message now has `temperature_c` (float64, °C) and `valid` (bool). Both `normalize` helpers and both `monitor` nodes output °C when `valid` is true and NaN when it's false. A clean build with only `/opt/ros/jazzy` sourced passes all tests, and I ran both nodes live to confirm.

## What changed
- **`src/thermal_interfaces/msg/ThermalReading.msg`**: replaced `float64 temperature_millic` with `float64 temperature_c` and added `bool valid`, each with a comment.
- **`src/thermal_interfaces/CHANGELOG.rst`**: added a `Forthcoming` entry at the top that marks this as a breaking change. I didn't change the version numbers, per CONTRIBUTING.
- **`src/thermal_py_monitor/thermal_py_monitor/conversion.py`**: `normalize(msg)` returns `msg.temperature_c`, or `math.nan` when `msg.valid` is false. I removed the `SCALE = 1000.0` constant because nothing uses it now. It wasn't listed as public in the README, but check that no downstream tool imports it.
- **`src/thermal_cpp_monitor/src/conversion.cpp`** and **`conversion.hpp`**: same behaviour; the invalid case returns `std::numeric_limits<double>::quiet_NaN()`. The signature is unchanged and the doc comment now mentions NaN.
- **Tests** (both packages): the old millidegree test is replaced by three cases: a valid reading returns 21.5, an invalid reading returns NaN even when a temperature is set, and a default-constructed reading (where `valid` is false) returns NaN.
- **Monitor nodes**: no code changes. Both already publish `normalize(msg)` to the same topics, so they get the new behaviour automatically. Package names, executables and topic names all match the README.

## How I verified it
1. **CI-style clean checkout:** I copied the tracked sources to `/tmp/thermal_ci` and used a shell with only `/opt/ros/jazzy` sourced. `colcon build` and `colcon test --return-code-on-test-failure --python-testing pytest` both exited 0: 7 tests, 0 failures (3 gtest, 3 pytest, plus CTest's wrapper). The build prints stderr for `thermal_py_monitor`; it's the existing `tests_require` setuptools warning and isn't related to this change.
2. **End to end:** I ran both `monitor` nodes from that build on a separate ROS domain and published to `/sensor/thermal`:
   - `{temperature_c: 21.5, valid: true}` → `/monitor/py_temperature_c` and `/monitor/cpp_temperature_c` both gave `21.5`
   - `{temperature_c: 21.5, valid: false}` → both gave `.nan`
3. **Your workspace:** I rebuilt `install/` with `colcon build` in a clean environment and reran the tests there (7 passed). Your sourced terminal therefore uses the new message rather than the old `temperature_millic` build. The install paths are the same, so any new terminal will pick it up.

## Other notes
- **Breaking change:** any other node or bag that uses the old `temperature_millic` field has to be updated or rebuilt.
- **C++ library not installed:** `thermal_cpp_monitor` installs its header but not the `thermal_cpp_monitor_conversion` library. Downstream C++ tools therefore can't actually link to `normalize` from the install tree. This was already the case and I left it alone because it's outside this change, but it's worth fixing if the README's "downstream tools call these helpers directly" matters for C++.
- **No test for `thermal_interfaces`:** I didn't add a test to that package itself. The consumer tests in both packages use the new fields.
- Nothing is committed. `/tmp/thermal_ci` is a disposable copy you can delete.
